# DECISIONS.md — judgment calls made while building the booking platform

Format: date · decision · why · how to reverse.

1. **Build inside SAMA-CRM instead of a new repo** (owner's choice, 2026-09-07). One Next.js app, one Supabase project, one Vercel project (`sama-crm`), one WhatsApp webhook. Guest site lives under `src/app/[locale]/(guest)`, back-office screens join the existing CRM `(app)` group.
2. **Keep Next.js 14 / React 18 / Tailwind 3** (the CRM's versions) instead of the prompt's Next.js 15. Upgrading a live app mid-build is the wrong risk to take unsupervised. Nothing in the booking engine needs Next 15.
3. **Two root layouts.** The CRM root layout moved to `src/app/(crm)/layout.tsx` (URLs unchanged) and the guest site gets its own root layout at `src/app/[locale]/layout.tsx` so `<html lang dir>` comes from the URL locale, not the CRM cookie. `next-intl` (v3, Next 14 compatible) handles `/en` `/ar` routing and messages; the CRM keeps its existing cookie-based `useLang()` — the two never mix.
4. **No `bk_guests` table — guests are CRM `contacts`.** The CRM already keys guests by E.164 phone. `bk_bookings.contact_id → contacts.id`; the booking function upserts the contact (name/email/lang/nationality) without touching consent fields.
5. **No `bk_staff` table — staff are CRM `profiles`.** Roles: `super_admin` = admin (everything), `reservation_desk` = front desk (bookings, calendar, blocks, messaging queue; no rates/settings/staff/audit).
6. **`bk_bookings` mirrors into CRM `bookings` by trigger** (same `id`, same `ref`, `room_type` = CRM canonical value, status mapped Confirmed/Cancelled/Completed). Keeps the inbox guest panel, `last_stay` stamping, win-back and birthday automations working. The mirror is additive only (no CRM columns changed).
7. **CRM automations `booking_created`, `pre_arrival`, `post_stay` set to `enabled=false`** to avoid double-messaging — the booking engine now sends confirmation, pre-arrival (3 days before, 10:00) and post-stay (1 day after, 11:00) with the approved Meta templates. `birthday` and `win_back` stay on. Reverse: toggle them back on in `/automations` (and turn off the channel switches in `/settings`).
8. **Room types = the six real ones** from `Hotel Information 2.xlsx`, with `crm_value` equal to the CRM `ROOM_TYPES` strings so both systems agree. Unit split 14/14/14/8/5/5 and rates 50–95 OMR are placeholders (only 60 total and 14 chalets are confirmed).
9. **Taxes:** service charge 8 % and tourism fee 4 % on the room subtotal; VAT 5 % on room + fees (`vat_on_fees` toggle). All rounded to 3 decimals (baisa).
10. **Availability is computed per night** (min over nights of active rooms − room blocks − type stop-sells − overlapping bookings). Double booking prevented with `pg_advisory_xact_lock(hashtext(room_type_id))` inside `bk_create_booking` plus a re-check.
11. **Scheduler = Vercel Cron every 15 min (`vercel.json`, team is on Pro) + pg_cron every 10 min as belt-and-braces**, both hitting `/api/cron/dispatch`. Auth: `Authorization: Bearer <secret>` where the secret is `bk_settings.cron.secret` (generated by migration, readable only via service role) — Vercel Cron sends `CRON_SECRET` env if set; either is accepted. This avoids needing new Vercel env vars for the scheduler.
12. **Booking-page tokens** are HMAC-SHA256 of the ref keyed by `BOOKING_TOKEN_SECRET` if set, else derived from `SUPABASE_SERVICE_ROLE_KEY` (already secret, already on Vercel).
13. **Hotel contact details, links and review URLs live in `bk_settings`** (editable in `/settings`), not env vars. Env only holds credentials.
14. **Email templates are hand-built HTML** (inline styles, bilingual per guest's preferred language) instead of React Email — fewer dependencies, same result, matches the CRM's existing email shell.
15. **WhatsApp bodies** match Section 5 of the kickoff prompt variable-for-variable. Dates in messages are formatted `Fri 12 Sep 2026` (EN) / Arabic long date (AR); totals as `123.500`.
16. **Photos**: the owner's Website/Pictures folder was resized to ≤1800 px and committed under `public/images/` (hero, rooms, facilities). Types without photos (Sama Suites) reuse Deluxe/Chalet shots and are flagged in HANDOFF.md.
17. **Booking refs** use `SAMA-YY-XXXXXX` (6 unambiguous alphanumerics), compatible with the CRM's `SAMA-YY-…` convention.
18. **Rate-limit** on the public booking action: in-memory token bucket per IP, 10/min per instance (good enough on Vercel; noted in HANDOFF).
19. **Legacy CRM booking screens retired.** `/bookings` → `/reservations` and `/bookings/new` → `/reservations/new` (redirects in `next.config.mjs`). The old form wrote CRM `bookings` directly with no inventory or pricing; every booking now goes through `bk_create_booking`. The mirror keeps CRM `bookings` populated.
20. **Messaging retry ladder** = 1 attempt + 3 retries at +5 min, +30 min, +3 h (`decideRetry`), then `failed`. Meta template-not-approved (132001/132000/132012) and undeliverable (131047/131026/131021) errors never retry; rate limits and 5xx do.
21. **Meta error codes are parsed from the error text** the existing `sendWhatsAppTemplate` returns — no second Graph call.
22. **Skipped rows** (booking cancelled, channel off, no email/phone) are recorded on `bk_scheduled_messages` only, not in `bk_message_log` — they are not attempts.
23. **Email sends reuse the CRM `sendEmail`** (HTML only); the plain-text version feeds the CRM inbox body and logs. If Resend rejects the sender, one retry goes out from `onboarding@resend.dev` and is flagged `fallback_sender`.
24. **Guest pages that read the database render per request** (`force-dynamic`); contact/policies/the-peak are ISR (10 min) with default settings as fallback — a Supabase outage can never fail a Vercel build.
25. **Staff shell is responsive**: fixed sidebar ≥ 1024 px, drawer + top bar below (front desk on a phone). Content padding tightens on small screens.
26. **Staff booking default message language** follows the guest's country code (Oman/GCC → Arabic, else English) until staff change it.
27. **Local QA without credentials**: `scripts/mock-supabase/` emulates PostgREST + the `bk_*` RPCs + GoTrue in memory (seeded from migration 0006) so `npm run e2e:local` runs the full Playwright suite anywhere. It is a stand-in, not the truth — the SQL functions remain the source of truth and the post-deploy checks in HANDOFF §9 must still be run.
28. **Sandbox network limits** (no `*.supabase.co`, `*.vercel.app`, Google Fonts, GitHub push): fonts are self-hosted from `@fontsource` files under `src/fonts/`; runtime verification against the real project is deferred to the first deploy (HANDOFF §9).
29. **Add-ons are catalogue-priced, untaxed by default.** `bk_addons.taxable=false` means the price is a final amount added after the room taxes (APEX is a third-party attraction; the transfer is a flat fee). A `taxable=true` add-on joins the taxable base instead. Prices always come from the database — the client only sends slug + quantity + note.
30. **Add-ons are "requested" until staff confirm them** (`bk_booking_addons.status`); the guest sees "Requested — we will confirm by WhatsApp". Cancelling the booking cancels its add-ons. WhatsApp templates are unchanged (their total already includes add-ons); emails list the lines.
31. **Room counts removed from guest copy** (owner's request, 8 Sept): no "sixty rooms", "six ways", "14 chalets" — the JSON-LD `numberOfRooms` stays for search engines.
32. **Images are served as WebP only** (`next.config.mjs`): AVIF encoding was 5–10× slower on first hit for no visible gain on these photos, and it made cold page loads time out in the sandbox.
33. **New photos (8 Sept)**: the owner's 2023 set replaced the room galleries (4–6 real photos per type, each type from its own folder), The Peak page uses the café interiors, facilities strip and contact page use the new pool/restaurant/kids/chalet-courtyard shots. Hero stays the canyon view. The `_web` / `_web2` folders in the owner's OneDrive Website folder are the resized copies and can be deleted.

34. **Shared WhatsApp number with the SAAS project (8 Sept)**: the hotel sends from the SAAS number instead of registering its own. Meta delivers a number's webhooks to exactly one callback, so the hotel takes the number's callback (an `override_callback_uri` on the business phone number — Meta's most specific override, with the WABA-level one as fallback — leaving the SAAS app's dashboard config untouched) and relays to SAAS what is SAAS's: inbound messages from its admin numbers (`WHATSAPP_FORWARD_SENDERS`) and every delivery receipt, re-signed with the shared app secret (`src/lib/whatsapp-forward.ts`). Guest conversations never reach the SAAS bot (it answers unknown senders with "this is an automated number"). Webhook registration, template submission (`src/lib/messaging/templates/meta-templates.ts`) and adopting the number as the site's contact are one-click actions on `/messaging/whatsapp` (`src/lib/whatsapp-admin.ts`), so no Meta dashboard work is needed beyond copying the Vercel variables. The verify token is accepted under the SAAS variable name too.
